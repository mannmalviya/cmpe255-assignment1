  2. What I found

  The biggest finding: this data is a template.

  97.3% of all 16,000 rows contain the word "feel", "feeling", "feels" or
  "felt". 37.9% start with the exact words "i feel" or "im feeling".

  So almost every row looks like this:

  ▎ i feel &lt;adjective&gt; because ...

  The frame is always the same. Only the adjective changes. And the adjective is
  the answer.

  Look at the top words for each emotion. I found them with a proper method
  (log-odds with a shrink prior), not raw counts:

  ┌──────────┬────────────────────────────────────────────┐
  │ Emotion  │               Its own words                │
  ├──────────┼────────────────────────────────────────────┤
  │ joy      │ successful, glad, satisfied, confident     │
  ├──────────┼────────────────────────────────────────────┤
  │ sadness  │ exhausted, miserable, punished, melancholy │
  ├──────────┼────────────────────────────────────────────┤
  │ anger    │ irritable, greedy, offended, resentful     │
  ├──────────┼────────────────────────────────────────────┤
  │ fear     │ terrified, shaken, vulnerable, nervous     │
  ├──────────┼────────────────────────────────────────────┤
  │ love     │ sympathetic, caring, loving, longing       │
  ├──────────┼────────────────────────────────────────────┤
  │ surprise │ amazed, impressed, curious, surprised      │
  └──────────┴────────────────────────────────────────────┘

  Every list is just emotion adjectives. Nothing else.

  Why this matters a lot for your question. An LLM normally wins because it
  understands word order, negation, and sarcasm. A TF-IDF model cannot do any of
  that. But this task does not need any of that. It needs you to spot one
  adjective. So I predict the LLM's win will be small. I wrote this down now,
  before any model runs. That way it is a prediction, not an excuse later.

  Other numbers:
  - Median length: 17 words. Max: 66. So 128 tokens is plenty for any
    transformer. Nothing gets cut.
  - Length tells you nothing about the emotion. The gap between the wordiest
    class (love, 20.7) and the shortest (sadness, 18.4) is 2.3 words. The spread
    inside the data is 11 words. So length is noise. I will not build a length
    feature.
  - Vocabulary: 15,212 different words. 51.4% appear exactly once. Those are
    useless for learning. I will drop them with min_df=2. That cuts the feature
    space in half for free.
  - Just 49 words cover half of all text (i, feel, and, to, the...). TF-IDF
    already squashes these. So no stopword list. Removing them by hand would
    break the template and kill negation words.
  - Zipf's law fit: R² = 0.97. This is normal English, not junk.

  The trap to watch: surprise has the most distinct words of all six classes.
  But it will still be the hardest to predict. Why? It only has 572 training
  rows. Joy has 5,362. Size beats separability. This is the main risk in the
  whole study.

  One odd row found: train_14842 talks about a console game called "shinobi". It
  is off-topic. I flagged it for Phase 6.

  2. Length distribution — histogram plus per-class density (to show they

  4. Vocabulary coverage curve

  already reported those counts.

  4. The standing requirement

  Research question: For a multi-class text classification task, does a small
  open-weight LLM beat a classical ML model — and is it worth the extra latency
  and compute?

  Hard rules:
  - One split. Frozen in data/processed/. Test never touches training or tuning.
    Each chunk says which split it used.
  - Baseline first. No model before the naive baseline.
  - Latency is measured. Warm up, then 200+ runs. Report p50 and p95. Single-row
    and batch, separately.
  - Every timing carries the hardware stamp, in the JSON, next to the number. If
    hardware changes, stop and re-run.
  - Seeds set. Versions pinned. All metrics saved as JSON.
  - Honest results. If the LLM loses, say so.

  This chunk used: train only. val and test were not read.

  2. What I found

  First: cleaning does nothing. I ran the full clean-up pipeline (lowercase,
  strip punctuation, fix unicode) on all 20,000 rows. 0 rows changed. So I use
  no cleaning step at all. I proved it instead of guessing.

  Second, and this is the big one. I found 52 texts that appear more than once.
  51 of those 52 have a different label each time. Only 1 is a plain copy.

  Look at this. The same sentence, two labels:

  ┌───────────────────────────────────────────────────┬──────────┬──────────┐
  │                       Text                        │ in train │ in test  │
  ├───────────────────────────────────────────────────┼──────────┼──────────┤
  │ i feel cared for and accepted                     │ joy      │ love     │
  ├───────────────────────────────────────────────────┼──────────┼──────────┤
  │ i feel so weird and scattered with all wonders... │ fear     │ surprise │
  └───────────────────────────────────────────────────┴──────────┴──────────┘

  Why this happened: whoever built the dataset removed copies where the text and
  the label matched. So the only copies left are the ones where two humans 
  disagreed.

  Why this is bad news, not good news. Normally, train/test overlap is cheating
  — the model memorises the answer and gets a free point. Here it is the
  opposite. If the model learns "cared for and accepted = joy" from train, it
  will be marked wrong on test, where the answer is love. These rows are traps.

  So there is a hard ceiling. 14 test rows (0.7%) are traps. No model can score 
  above 99.30% accuracy. The real ceiling is lower, because I can only spot the
  ambiguous rows that got duplicated. There are certainly more that appear only
  once.

  Third: which emotions do humans mix up? I counted which label pairs collide,
  and compared it to what chance would give:

  ┌─────────────────┬───────┬─────────────┬────────────────┐
  │      Pair       │ Found │ Chance says │ How much worse │
  ├─────────────────┼───────┼─────────────┼────────────────┤
  │ joy ↔ love      │    29 │         3.7 │ 7.8x worse     │
  ├─────────────────┼───────┼─────────────┼────────────────┤
  │ fear ↔ surprise │     7 │         0.6 │ 12.3x worse    │
  ├─────────────────┼───────┼─────────────┼────────────────┤
  │ joy ↔ sadness   │     0 │        13.1 │ never happens  │
  └─────────────────┴───────┴─────────────┴────────────────┘

  This flips a Phase 3 conclusion. Phase 3 said joy and sadness use the most 
  similar words. But humans never mix them up. Of course not — one is happy, one
  is sad.

  So: sharing words is not the same as being confusable. joy and love share
  fewer words, but they mean almost the same thing, so people mix them up
  constantly.

  I wrote a prediction for Phase 17: the model's mistakes should mostly be
  joy↔love and fear↔surprise, and almost never joy↔sadness. If that holds, the
  model fails where humans fail. That means the leftover error is real
  ambiguity, not a bad model.

  2. What I found

  TF-IDF is tiny and fast. Fits in 0.35 seconds. Saves to 0.3 MB. Remember that
  number — the LLM files will be 10,000x bigger.

  Dropping words seen only once cuts the vocabulary in half (15,188 → 7,257) and
  costs only 0.5 words per row. Basically free.

  Nothing breaks. 0 test rows end up with an empty feature vector, in any setup.
  So TF-IDF has no blind spot here for the LLM to beat it on.

  Token length is settled forever. I checked with the real transformer
  tokenizer. Longest text = 87 tokens. Zero rows go over 128. So 128 is safe for
  the whole study, with room to spare.

  The embeddings gave a split result. This is the interesting part.

  Zoomed out, the six classes sit on top of each other. I measured the average
  distance between class centres. joy's own centre beats its nearest rival by
  0.004. That is nothing.

  Zoomed in, the neighbourhoods are good. I asked: of your 10 nearest
  neighbours, how many share your label? Answer: 49.2%, versus 23.7% by chance.
  And a plain neighbour vote gets 65.8% accuracy with no training at all.

  Quick check that it works:

  ▎ Ask: "i feel so happy and grateful today"
  ▎ Get back: 0.871 joy "i feel happy and grateful to you all"

  So the embeddings are fine. They just do not separate the classes into big
  blobs.

  This gives me two predictions for the next chunks:
  - Phase 8 (KMeans) will fail to find the emotions. KMeans works from class
    centres, and the centres overlap. The clusters it finds will be about topic

  - Loose setting → everything becomes 1 big blob

  area" stops meaning anything. I report this as a real negative result. I did
  not keep tuning until a number looked good.

  checked normalisation and said clean. Both were right and both were blind,
  because href looks like a normal English word.

  2. What I found

  Job 1: near-duplicates — found hidden leakage

  Phase 5 only looked for exact copies. I looked for almost copies.

  Look at this pair:

  ┌───────┬─────────────────────────────────────────────┬───────┐
  │       │                    Text                     │ Label │
  ├───────┼─────────────────────────────────────────────┼───────┤
  │ train │ i didn t think that it would come that fast │ anger │
  ├───────┼─────────────────────────────────────────────┼───────┤
  │ val   │ i didnt think that it would come that fast  │ anger │
  └───────┴─────────────────────────────────────────────┴───────┘

  Same sentence. One has a stray space. A string check sees two different rows.
  A model sees one.

  Found 138 such pairs crossing the split line. And here is the key difference
  from Phase 5:

  ┌──────────────┬────────────────────┬────────────────────────┐
  │              │  Phase 5 (exact)   │     Phase 9 (near)     │
  ├──────────────┼────────────────────┼────────────────────────┤
  │ Pairs found  │                 19 │                    138 │
  ├──────────────┼────────────────────┼────────────────────────┤
  │ Labels agree │                 0% │                    88% │
  ├──────────────┼────────────────────┼────────────────────────┤
  │ Effect       │ model loses points │ model gets free points │
  └──────────────┴────────────────────┴────────────────────────┘

  Phase 5's copies all had different labels — traps. These near-copies mostly
  have the same label — gifts.

  2.10% of test rows are near-copies of a training row with the same answer.

  Put together with Phase 5's 0.70% traps: about 1.4% of any test score is an 
  artifact of how the benchmark was built, not real skill. I did not delete
  anything. Every model faces the same test set, so comparing models is still 
  valid — and that is your actual question. But a final score of 89% should be
  read as "89%, about 1.5 points of which is benchmark noise."

  Job 2: LSH search — it lost

  I predicted LSH would work well. It did not. I also flagged a counter-risk
  last chunk. The counter-risk is what happened. I am reporting it straight.

  ┌──────────────────────┬───────────┬────────────────────────┐
  │        Method        │  Recall   │         Speed          │
  ├──────────────────────┼───────────┼────────────────────────┤
  │ Plain exact search   │      100% │ 0.234 ms               │
  ├──────────────────────┼───────────┼────────────────────────┤
  │ Best LSH setting     │     62.5% │ 0.986 ms — 4.2x slower │
  ├──────────────────────┼───────────┼────────────────────────┤
  │ Fastest LSH settings │ under 23% │ faster, but useless    │
  └──────────────────────┴───────────┴────────────────────────┘

  Every one of 16 settings is either slow or bad. There is no good option.

  Why, reason 1: the neighbours are not close enough. LSH works when a text's
  true neighbours score 0.9+ similarity. Here, a typical 10th-best neighbour
  scores only 0.54 — sitting right on the shoulder of the ordinary pile. So the
  hash cannot tell "neighbour" from "random other row".

  I checked this against the LSH formula. Theory predicts 53% recall at the best
  setting. I measured 62.5%. Theory and measurement agree. So this is not a bug
  in my code. It is the shape of the data.

  Why, reason 2: exact search is already stupidly fast. Searching 15,923 rows is
  one matrix multiply. Modern CPUs do that in under a millisecond. LSH replaces
  it with hash lookups and set merging in Python — and the bookkeeping costs
  more than the maths it skips.

  When would LSH win? At a million rows, not sixteen thousand. Or on a
  fine-tuned embedding space where neighbours really do sit at 0.9. I said both
  in the doc so the negative result is not overclaimed.

  The pattern worth noticing

  This is now two phases in a row where the fancy method lost to the simple one,
  for the same reason: the simple operation is already so cheap that overhead
  beats cleverness.

  - Phase 8: KMeans could not beat "always guess joy"
  - Phase 9: LSH could not beat one matrix multiply

  That is a warning for Phases 13–15. This dataset is small, short, and
  templated. It is a hard place for expensive methods to earn their cost.

  2. What I found

  One word decides the answer

  This is the big one. Look at these rules:

  ┌──────────────────────┬───────────────────────┐
  │         Rule         │ How often it is right │
  ├──────────────────────┼───────────────────────┤
  │ sympathetic → love   │ 54 out of 54 times    │
  ├──────────────────────┼───────────────────────┤
  │ apprehensive → fear  │ 58 out of 58 times    │
  ├──────────────────────┼───────────────────────┤
  │ listless → sadness   │ 48 out of 48 times    │
  ├──────────────────────┼───────────────────────┤
  │ impressed → surprise │ 61 out of 63 times    │
  └──────────────────────┴───────────────────────┘

  100% right. One adjective, and you know the answer.

  Phase 3 said "the key words are emotion adjectives". This turns that into a
  hard probability. It is the clearest statement of what this benchmark really
  is.

  Word pairs add nothing

  I tested the question your whole study rests on, in its cheapest form: does 
  knowing two words beat knowing one?

  I compared 5,446 word pairs against their best single word.

  ┌────────────────────────────────────────┬──────────────────────┐
  │                                        │                      │
  ├────────────────────────────────────────┼──────────────────────┤
  │ Average gain from adding a 2nd word    │ −0.9 points (worse!) │
  ├────────────────────────────────────────┼──────────────────────┤
  │ Pairs that beat their best single word │                39.8% │
  ├────────────────────────────────────────┼──────────────────────┤
  │ Pairs gaining more than 10 points      │                 1.1% │
  └────────────────────────────────────────┴──────────────────────┘

  Adding a second word makes the rule slightly worse on average. In the figure,
  every point sits on the diagonal line — meaning "no gain".

  And there are no real phrases in the top gains. No "not happy". No "so tired".
  No idioms. The word combinations that bigrams are supposed to catch are not 
  in this data.

  So I predict: Phase 12's bigrams will not help. They cost 4.6x the vocabulary
  for nothing. Cross-validation should pick plain single words.

  Important limit, and I wrote it in the doc. Apriori only sees what a
  bag-of-words sees. It cannot see word order, or long-range meaning, or world
  knowledge. So the honest conclusion is narrow: inside bag-of-words, combining 
  words adds nothing. If the fine-tuned LLM in Phase 15 wins big, that win must
  come from something Apriori literally cannot look at. That is the point — I
  ruled out the cheap explanation, so any later win has to be the expensive one.

  Two things I had to fix, and they are findings

  1. The strongest "rule" in the data is website junk. href → a + http, lift
  79-88, in every single class. That is the Phase 8 HTML bug showing up again,
  found independently. I reported it, then excluded those 13 tokens so the phase
  could say something about emotion.

  2. Looking inside one emotion finds nothing useful. After removing the HTML,
  the top rule became don → feel + t — which is just don't split in half when
  punctuation was stripped. Why? Inside one emotion, every row already shares "i
  feel ...", so the strongest pairs are whatever else happens to be glued
  together. Emotion is constant inside a class, so it is invisible there. The
  useful question was always "which words predict a class", not "which words sit
  together inside one".

  Why it lost — the model refuses the six boxes

  143 answers (7.15%) were not one of the six labels. I counted all of them as
  wrong, as the rules say. The model said things like:

  ▎ stress · pain · anxiety · uncertainty · peace · curiosity · guilt

  61 different words. And 24% of surprise rows came back like this. For those
  rows it said "curiosity" or "confusion". Once it even said "amazed" — the word
  sitting right in the text.

  Here is the thing: those answers are not really wrong. Anxiety is a kind of
  fear. Curiosity is a kind of surprise. The model knows more emotion words than
  the dataset allows, and a one-line instruction did not make it squeeze them
  into six boxes.

  I did not add a synonym map like "anxiety → fear". I would be writing it after
  reading the test answers. That is cheating on test.

  The bigger problem is judgement, not format

  Even on rows it answered properly, it only got 53.6% right. The biggest single
  mistake:

  It called 185 "joy" rows "love". That is 27% of all joy rows.

  This is the joy/love line again — the same one Phases 5, 8 and 12 all flagged
  as a rule someone made up, not a real split in the language. The SVM learned
  where this dataset draws that line from 17,923 examples. The zero-shot model 
  saw zero examples, so it drew its own line, much wider.

  Two more patterns: it dumps fear into sadness (42% of fear rows), and it
  almost never says "fear" or "surprise" at all.

  Latency detail worth knowing

  Batching barely helps. Going from batch 1 to 32 only doubles speed, and batch
  128 is slower. The bottleneck is the Python generation loop, not the GPU. A
  proper serving engine would help somewhat — but the gap is 1,000x, and those
  tools usually buy about 10x.

  Where DistilBERT really wins: long texts

  On texts of 46+ words: SVM 75%, DistilBERT 91% (fixed 11, broke 2, p = 0.02).

  Why: long texts contain several emotion words. The SVM just adds them all up.
  DistilBERT can tell which one actually belongs to the writer. Phase 6 said to
  check exactly this.

  Where it does NOT win: negation

  A common belief is that transformers win by understanding "not". Not here.
  DistilBERT fixes negation rows at exactly the same rate as every other row.

  The biggest discovery: the labels disagree with themselves

  Some words are labelled half one emotion, half another, in the training data
  itself:

  ┌───────────────┬─────────────────────────────┬──────────┬────────────────┐
  │     Word      │ How humans labelled it in   │   SVM    │  DistilBERT    │
  │               │          training           │  right   │     right      │
  ├───────────────┼─────────────────────────────┼──────────┼────────────────┤
  │ agitated      │ anger 51% / fear 47%        │      46% │            54% │
  ├───────────────┼─────────────────────────────┼──────────┼────────────────┤
  │ passionate    │ love 52% / joy 44%          │      43% │            43% │
  ├───────────────┼─────────────────────────────┼──────────┼────────────────┤
  │ stressed      │ sadness 52% / anger 37%     │      30% │            50% │
  ├───────────────┼─────────────────────────────┼──────────┼────────────────┤
  │ amazed        │ surprise 94%                │      78% │           100% │
  │ (check)       │                             │          │                │
  └───────────────┴─────────────────────────────┴──────────┴────────────────┘

  A word humans labelled consistently gets learned perfectly. A word humans 
  split 50/50 is a coin flip, for every model. This also explains the
  sadness↔anger mystery from Phase 12: it is mostly stressed and hated.

  I found these words after reading the errors, so I clearly marked this as
  exploratory, an idea to test, not a proven result.

  The 56 rows no trained model gets right

  Many look like bad labels:

  ▎ "whenever i put myself in others shoes and try to make the person happy" → 
  ▎ labelled anger
  ▎ "i could feel his breath on me and smell the sweet scent of him" → labelled 
  ▎ joy (every model says love)

  I said in the doc that this is my reading. But no model should be blamed for
  these.

  The prompted LLM's one real strength

  On 14 rows, Qwen zero-shot was right when both trained models were wrong:

  ▎ "i feel hated in cempaka" → sadness. Both trained models said anger, keying 
  ▎ on the word "hated". Qwen read the sentence: being hated is sadness; hating 
  ▎ is anger.

  That is real understanding. But it is 14 rows out of 2,000, inside a model
  that gets 1,005 wrong.

  2. The answer to your question

  It depends on how you use the model. The two ways give opposite answers.

  ┌────────────────────────┬────────┬─────────┬─────────────┬─────────────┐
  │                        │ Macro  │   p95   │ Extra cost  │  Worth it?  │
  │                        │   F1   │         │   / month   │             │
  ├────────────────────────┼────────┼─────────┼─────────────┼─────────────┤
  │ Linear SVM (the bar)   │  0.858 │ 0.25 ms │           — │ —           │
  ├────────────────────────┼────────┼─────────┼─────────────┼─────────────┤
  │ Prompted small LLM     │  0.411 │   61 ms │      +$3.36 │ ❌ No       │
  │ (Qwen 1.5B)            │        │         │             │             │
  ├────────────────────────┼────────┼─────────┼─────────────┼─────────────┤
  │ Fine-tuned small model │  0.898 │  18 ms  │      +$0.40 │ ✅ Yes,     │
  │  (DistilBERT)          │        │  on CPU │             │ modestly    │
  └────────────────────────┴────────┴─────────┴─────────────┴─────────────┘

  - Just asking an LLM loses badly. It is worse, slower, and thousands of times
    costlier. Giving it examples made it worse.
  - Training a small model on the data wins. It is better than the SVM on every
    emotion, and the win is statistically certain. Winning by 3+ points is
    probable (85%), not certain.
  - Why: this dataset's labels are rules someone chose (joy vs love, what
    "stressed" means). A trained model learns those rules. A prompted model
    brings its own.

  My recommendation in the report:
  1. Use fine-tuned DistilBERT on a CPU: 18 ms, 40 cents a month, about 31,500
     fewer mistakes a month.
  2. Keep the SVM as the fallback. It is tiny and nearly as good.
  3. Do not use a prompted small LLM for this.
  4. Fix the labels before buying a bigger model. Over half the remaining errors
     are cases where humans themselves disagree.

  The report also has an honest corrections table listing every mistake I made
  and fixed along the way, and a limits section that says plainly where these
  results should not be generalised.
